# 120 Bridge Constitution

## Core Principles

### I. 시민의 선택과 디지털 포용

서비스는 시민의 명시적인 상담사 연결 요청을 다른 상담 규칙보다 먼저 처리해야 한다.
추가 질문이나 AI 이용 재권유로 연결 절차를 지연해서는 안 된다.
근거가 충분한 일반 문의는 짧게 안내하되 언제든 사람 연결 경로를 제공해야 한다.

시민은 한국어 음성·자막·텍스트로 같은 상담을 진행할 수 있어야 한다.
한 번에 하나의 확인 질문을 제시하고 쉬운 한국어를 사용해야 한다.
상태는 색상만으로 전달해서는 안 된다.
같은 필수 정보는 최초 질문 포함 최대 두 번까지 확인하며,
해당 질문은 낮은 답변 신뢰 횟수와 구분해야 한다.

### II. 검증된 근거에 따른 안내

사실 안내와 담당 창구 추천은 검증된 유효 근거에 연결되어야 한다.
자료가 없는 경우 원인·수치·연락처·부서명을 만들어내서는 안 된다.
시민에게 제공하는 사실에는 출처와 기준일을 표시하고,
기준일·시행일·원문 확인일이 미확인이면 그 상태를 보존해야 한다.

적용 지역은 문의 목적에 따라 배출지·발생지·거주지 등을 구분해야 한다.
기존에 확인된 같은 목적의 정보는 재사용하고,
게시일만으로 최신성·시행 여부·처리 권한을 확정해서는 안 된다.
대체된 정책 항목과 미변경 업무분장 정보는 별도로 검토해야 한다.
현재 MVP는 사전 수집된 자료를 사용하고 상담 중 웹 검색으로 근거 범위를 바꾸지 않는다.

### III. 상담 맥락과 확인 상태 보존

복합 문의는 항목별로 하나씩 진행하고,
안내한 내용과 미해결 내용을 구분해 원문·요약·이관 사유를 함께 전달해야 한다.
시민이 이미 제공한 설명을 처음부터 반복하도록 요구해서는 안 된다.

요약은 승인·부분 수정·미확인 상태를 구분해야 한다.
매우 불만과 연결 의사가 함께 있거나 명시적으로 확인 생략을 요청한 경우에는
확인을 강제하지 않고 미확인 요약과 생략 사유를 전달해야 한다.
무응답을 승인으로 취급해서는 안 된다.

전달 후 수락 전 정정은 같은 상담 건의 최신 버전으로 다시 전달해야 한다.
이전 이력·정정문·수신 상태를 보존하고 중복 대기열을 만들지 않아야 한다.
수신 확인 전 전달 완료, 상담사 수락 전 연결 완료를 안내해서는 안 된다.
현재 시민 화면은 상담사가 수락하면 시연 표기가 있는 연결 완료 화면으로 끝나며,
이후 처리 결과는 콘솔에만 기록한다.

### IV. AI 후보와 책임 있는 사람 판단

AI의 출력·신뢰·감정 판정은 참고 후보이며 정확성이나 처리 권한의 보증이 아니다.
이관 여부·질문 한도·상태 전이·출처 유효성·확인 상태는
검증된 서버 규칙으로 결정해야 한다.
LLM 오류가 명시적 사람 연결 버튼·키 입력을 막아서는 안 된다.

담당 창구는 근거와 불확실성을 제시하고 최종 선택은 상담사가 해야 한다.
외부 기관도 처리 목적에 맞으면 후보로 포함하되,
근거가 부족하면 후보 없음과 이유를 표시해야 한다.
상담사의 처리 결과는 개인정보를 제거한 개선 후보로만 보존하고,
공식 원문 검증·검토 승인·회귀 시험 전에는 답변 자료로 자동 반영해서는 안 된다.

### V. 검증 가능한 최소 구현

시연 대본은 대표 회귀 사례이며 지원 질문 목록이나 제품의 고정 응답이어서는 안 된다.
대본 밖 표현·조건·지역·복합 문의와 근거 없는 문의에도 같은 규칙을 적용해야 한다.
과도한 기능 추가보다 안내·사람 연결·확인 요약·콘솔 전달의 전구간 동작을 우선한다.

실제 결과 없이 AI 해결률·처리시간·상담사 생산성 향상을 주장해서는 안 된다.
모의 지표는 모의임을 표시하고 미확인 종료를 AI 해결로 세지 않아야 한다.
비율의 분자·분모는 같은 대상 상담과 관찰 구간을 사용해야 한다.
계획·문서 검토·fixture·영상과 실제 구현·모델 호출·제출 배포 성공을 구분해야 한다.

## Service Boundaries and Data Protection

- 현재 범위는 서울시·자치구 생활행정 전반의 문의 접수와
  검증 근거가 있는 내용의 안내, 미해결 문의의 모의 상담사 인계다.
  전 분야·전 자치구의 직접 답변 가능성을 보장하지 않는다.
- 실제 전화망·행정 접수·개인 입금 조회·시민과 상담사 간 양방향 대화는
  이번 MVP에서 구현된 것으로 표현해서는 안 된다.
- 시연은 가상 민원·가상 개인정보로 진행한다.
  서버 비밀키·접근 토큰은 공개 코드·브라우저 번들·일반 로그에 노출해서는 안 된다.
  시민 세션과 콘솔의 접근 권한을 구분하고 다른 상담 건의 무단 조회를 막아야 한다.
- 개인정보가 포함된 상담 원문을 일반 개선 자료나 지표 보고서로 내보내서는 안 된다.
  운영용 동의·기록 보유·실제 상담사 검증은 파일럿에서 별도 확정한다.
- 개발 시간과 담당자 가용성은 최신 사용자 알림을 기준으로 계획에 반영한다.
  병렬 일정은 선행 조건과 담당자별 중복 금지를 지켜야 하며 완료 보장으로 제시하지 않는다.
  인프라·모델·키를 사용할 수 있다고 확인 없이 가정해서는 안 된다.

## Delivery and Quality Gates

1. 구현 전 명세·계획·태스크·데이터 모델·계약이 이 헌법과 일치하는지 확인한다.
   데이터 제약은 구현 태스크에서 정확한 필드와 원문 정의를 참조해야 한다.
   이 검토를 실제 기능 시험 통과로 기록해서는 안 된다.
2. 계약·이관 정책·근거 필터 등 중요한 동작은 수용 기준에 따른 시험으로 검증한다.
   공통 타입 이후 자료·모델·화면 fixture 작업은 병행할 수 있으나,
   실제 통합은 필요한 저장·인증·API 선행 조건을 충족해야 한다.
3. 기본 회귀와 독립 일반 문의, 정정 재전달·미확인 인계·중복·재시도·복구 경로를 검증한다.
   자료 개선 시험은 버전을 구분하고 승인 전 자료를 답변 근거로 사용하지 않는다.
4. 제출 HTTPS 환경에서 두 화면의 상태 공유·실제 모델 호출·음성/텍스트·접근 제어·
   새로고침과 재시작 복구를 검증한다. 로컬 성공이나 녹화만으로 제출 검증을 대체하지 않는다.
5. 무근거 사실 안내, 오래된 정책의 현재 사실 안내, 명시적 연결 차단,
   미확인 요약의 확인 완료 오표시, 정정 유실은 필수 완료 판정 실패다.
   미통과·미실행·접근 불가 전제와 후순위 항목을 숨기지 않고 기록한다.

## Governance

이 헌법은 기존 사용자 합의에서 도출한 프로젝트 원칙이다.
기능의 구체 범위·일정·담당·기술 선택은 명세와 계획에 두고,
템플릿의 예시 문구를 실제 프로젝트 의무로 해석하지 않는다.

새 명세·계획·태스크와 원칙에 영향을 주는 변경은 헌법 정합성을 점검해야 한다.
원칙에 어긋나는 설계를 문서의 하위 규칙이나 시간 부족을 이유로 묵시적으로 허용해서는 안 된다.
새로운 명시적 사용자 결정이 원칙을 바꾸는 경우에는
해당 결정·개정 이유·영향 문서를 기록하고 헌법과 관련 문서를 함께 갱신한다.

버전은 의미적 버전 규칙을 따른다.
원칙을 제거하거나 호환되지 않게 재정의하면 MAJOR,
새 원칙·거버넌스 요구를 추가하면 MINOR,
의미를 바꾸지 않는 표현·오탈자 수정은 PATCH를 올린다.
최초 제정은 1.0.0이며 최초 제정일은 보존하고 개정일만 갱신한다.
문서 검토로 규칙 준수를 확인한 사실과 실행 증거로 제품 동작을 확인한 사실은 구분한다.
