# 120Bridge MVP 구현·배포 명세

작성 기준일 2026-11-21 · 대상은 시민 상담 화면부터 상담사 콘솔, RAG, 제출 배포까지의 전체 MVP다.

제품 동작과 기존 수용 기준은 [기능 명세](spec.md), [API 계약](contracts/service.md), [데이터 모델](data-model.md)을 기준으로 삼는다. 이 문서는 새로 합의한 배포 구조, 상담사 바로 연결, 저장 책임과 각 작업의 완료 기준을 정한다. [기존 구현 계획](plan.md)의 단일 장기 실행 Node 및 파일 스냅샷 설계는 아래 Vercel·Cloud Run·Supabase 구조로 갱신한다. API와 데이터 모델 문서에서 충돌하는 부분은 구현 첫 단계에서 함께 맞춘다.

## 1. 현재 상태

| 항목 | 확인한 상태 |
| --- | --- |
| 시민용 웹 배포 | [Vercel 운영 주소](https://120-bridge.vercel.app/)가 응답한다. 운영 브랜치는 `Alexjung0115/120_Bridge`의 `master`, 앱 루트는 `frontend/`다. |
| AI 서버 배포 | GCP 서울 리전(`asia-northeast3`)의 `bridge-api-demo`에서 [직접 호출한 /health](https://bridge-api-demo-129844172635.asia-northeast3.run.app/health)가 HTTP 200과 `{"ok":true}`를 반환한다. |
| 웹 → AI 서버 | [연결 커밋 aa692c2](https://github.com/Alexjung0115/120_Bridge/commit/aa692c2)를 운영 브랜치에 반영했다. [운영 /api/ai/health](https://120-bridge.vercel.app/api/ai/health)에서 HTTP 200과 `{"ok":true}`를 실측했다. |
| AI 소스 선작업 | [FastAPI 소스·배포 절차](../../backend/README.md)와 내부 `/answer` 계약을 작성했다. 로컬에서 정상·근거 부족·타임아웃 응답을 시험했다. 실제 모델 연결은 후속이다. |
| 민원 DB | 팀원이 Supabase 연동을 진행 중이다. 테이블·마이그레이션·상담사 인증 및 배포 결과는 팀원 브랜치에서 확인이 필요하다. |
| RAG 자료 | 기존 문서와 복지사업 데이터를 결합해 432개 문서·2,044개 청크의 로컬 검증을 통과했다. [적재 준비 스크립트](../../scripts/prepare_rag.py)는 항목별 승인 전 자료에 답변 자격을 부여하지 않는다. Supabase 적재, 근거 승인, 검색·답변 실행 검증이 남아 있다. |

현재 운영에서 검증한 AI 경로는 헬스 체크다. 기능별 완료는 아래 수용 시험으로 판정한다.

## 2. 서비스와 데이터의 책임

| 구성 | 책임 |
| --- | --- |
| **Next.js · Vercel** | 시민·상담사 UI, 브라우저 음성 입출력, 시민 세션과 상담사 인증 검증, 상담 명령·이관 정책·상태 전이, Supabase 저장 및 대기열 조회. 일반 상담에서만 FastAPI를 호출한다. |
| **FastAPI · Cloud Run** | 받은 문의에서 근거 검색, LLM 구조화 응답·요약 후보 생성, 출처·관할·유효성 검증. 결과는 Next.js 서버로 반환하며 상담 상태를 직접 변경하지 않는다. |
| **Supabase · PostgreSQL** | 같은 프로젝트에서 민원 세션·대화·이관·이벤트와 RAG 문서·청크·임베딩을 서로 다른 테이블로 관리한다. 여러 요청과 인스턴스가 동일한 저장 상태를 읽는다. |

```text
일반 상담         브라우저 → Next.js 상담 API → 발화 저장 → FastAPI → RAG·LLM
                                        ← 검증된 응답 후보 ←
                          Next.js → 답변·출처와 상담 상태 저장 → 브라우저

상담사 바로 연결   브라우저 → Next.js 이관 API → Supabase 대기열
상담사 콘솔        브라우저 → Next.js 콘솔 API → Supabase 대기열 조회
```

- 공개 시연 점검 경로 `/api/ai/health`는 Cloud Run의 `/health`로 전달한다. 현재 rewrite는 `/api/ai/*`만 대상으로 한다. 실제 AI 기능을 붙일 때 공개 rewrite는 헬스 체크 경로로 좁히고, Next.js **서버**가 FastAPI의 추론 경로를 호출하도록 한다.
- AI 추론 요청은 서버 간 인증을 요구한다. Supabase 민원 기록을 읽고 변경하는 주체는 Next.js 서버다. FastAPI는 RAG에 필요한 자료만 읽고, 상담에 필요한 맥락만 전달받는다.
- Vercel의 프론트와 Cloud Run의 AI 서버는 독립적으로 배포한다. GCP 서울 리전과 현재 Cloud Run 서비스는 시연에 재사용한다. 상담사 연결은 웹 콘솔 접수와 모의 이관까지가 MVP이며, 실제 120 전화망·행정 접수 연동은 이후 범위다.

## 4. 민원 저장과 상담사 바로 연결

### 최소 저장 및 API

테이블 이름은 진행 중인 팀원 마이그레이션을 기준으로 확정한다. 최소한 아래 상태를 저장한다. 샘플 데이터는 가상으로 작성한다.

| 데이터 | 보존할 값 |
| --- | --- |
| 상담 세션과 문의 항목 | 세션 ID, 권한 확인에 쓰는 토큰 해시, 현재 상태·revision, 문의별 알려진 값과 누락 필드, 생성·수정 시각 |
| 대화 메시지 | 발화 순서·문자/음성 구분·원문, 이미 안내한 내용과 출처, AI 결과 또는 실패 사유 |
| 이관 건 | 상담 세션 ID, 동일 요청을 식별하는 명령 ID, 확인/미확인 정보, 생략·이관 사유, 상담사가 읽을 전달 기록, 대기 상태, 접수·담당 지정·완료 시각 |
| 처리 이벤트 | AI 안내 확인·이관 요청·접수·담당 지정·완료 시각, 담당자 가명, 결과 및 개선 후보 참조 |

Next.js가 `POST /api/sessions`, `POST /api/sessions/:id/turns`, `POST /api/sessions/:id/handoff-request` 및 `GET /api/console/queue`를 제공한다. 나머지 요약 확인·수정·조회·재시도·콘솔 명령은 [기존 API 계약](contracts/service.md)을 따른다. 작업 전에 다음 사항을 계약 문서에서 맞춘다.

1. **입력 먼저 저장.** 일반 상담은 발화를 저장한 뒤 FastAPI를 호출한다. 근거 부족·모델 오류·타임아웃·개인 조회 필요를 구별한다. 실패해도 원문과 이미 확인한 값이 남는다.
2. **버튼은 명시적 생략.** `상담사 바로 연결하기`는 `handoff-request`에 `trigger=button`과 바로 연결 의사를 전달한다. 기본 요약 확인·수정 흐름과 이 명령은 계약에서 구별한다. 상담 시작 직후에도 사용할 수 있고, 대화가 없으면 빈 문맥으로 접수한다.
3. **모델 호출 없이 등록.** 가장 최근에 저장된 원문·기존 안내·미해결 항목·실패 사유를 전달한다. 이미 확인한 요약과 개별 필드의 확인 여부는 유지한다. 생성된 요약이 없거나 시민이 확인하지 않았다면 그 상태를 콘솔에 표시하고 모르는 값은 비운다. 연결 요청 뒤 도착한 AI 응답은 상태를 되돌리지 않는다.
4. **접수와 재시도.** 세션 상태 변경과 대기열 등록을 한 DB 트랜잭션에서 처리한다. 세션당 이관 건은 하나이며, 동일 명령 재시도는 기존 이관 ID를 반환한다. DB에 `queued`와 접수 시각이 기록된 뒤에만 `접수됨 · 대기 중`을 표시한다. 실패는 재시도할 수 있게 표시한다.
5. **콘솔과 권한.** 상담사 인증 후 같은 대기열을 조회한다. MVP는 기존 1초 폴링을 사용한다. 원문·확인 상태·실패 사유·근거를 건별로 표시한다. 담당자 동시 지정은 DB에서 한 건만 성공시키고, 최종 창구 선택과 모의 완료는 상담사가 한다. 시민은 자기 세션만 조회할 수 있다.

## 5. RAG와 AI 답변

1. **같은 Supabase에 적재.** RAG 담당이 기준 문서와 GitHub의 복지사업 JSONL을 문서 ID 및 청크 ID로 upsert한다. 원문 URL·자료 버전·관할·시행 기간·검증 상태를 보존한다. 기존 검증 기록과 복지사업의 후보 검색 상태를 적재 과정에서 넘겨받는다.
2. **답변 가능 근거를 승인.** 복지사업 396건은 후보 검색 자료다. 사업별 최신 공식 근거와 대조한 항목만 시민 답변 자격을 부여한다. 신청방법 누락, 개인 선정 결과, 확인되지 않은 금액·자격을 모델이 추정해 채우면 안 된다. 상담 원문과 개선 후보는 공개 RAG 문서에서 분리한다. [데이터 수집 계획](data-collection.md)
3. **검색 규칙.** 해당 자치구의 자료와 적용 가능한 공통 자료를 사용한다. 관할·시행 기간·대체 관계·검증 상태를 적용하고, 문단별 결과에서 근거를 고른다. 의미 검색 단계에서 `pgvector`와 한 가지 임베딩 모델을 사용한다. 수집 청크와 질문에는 같은 모델·차원을 적용한다. 기본 검증 세트와 임계값 조정용 표본은 분리한다.
4. **AI 출력 계약.** FastAPI의 서버 간 추론 API는 문의·필요 문맥을 입력받아 해석 후보, 답변·되묻기 후보, 검증된 청크 ID·인용·기준일, 요약 후보를 반환한다. 검색 밖 ID, 인용 불일치, 관할·시행일 위반, 잘못된 JSON이면 사실 답변을 반환하지 않는다. Next.js가 기존 우선순위·질문 한도·이관 정책을 적용한다.
5. **대화 규칙.** 같은 필수 정보는 최대 두 번 묻고, 필수 질문은 낮은 신뢰 횟수에서 제외한다. 복합 문의는 하나씩 처리하고 미해결 항목만 이관 대상으로 표시하되 상담 맥락은 함께 넘긴다. 사실 안내마다 출처와 기준일을 표시하고, 음성은 한 번에 두 문장 이하로 읽는다. 모델과 키는 실제 구조화 한국어 응답 시험 이후 제출 기록에 적는다.

## 6. 배포, 설정 및 운영 확인

| 환경 | 설정 및 확인 |
| --- | --- |
| **GitHub** | 민원 DB·웹, AI 백엔드, 자료 순으로 변경을 통합한다. RAG 데이터는 별도 브랜치에 있으므로 필요한 버전을 통합하고 해시를 기록한다. 서버 소스와 의존성 파일은 Git에 두어 임시 Cloud Shell 폴더 없이 재배포할 수 있게 한다. |
| **Vercel** | Next.js 프로젝트 루트 `frontend/`, 운영 브랜치 `master`. 서버 함수에 Cloud Run 기본 주소·서버 간 인증 정보·민원 DB 접속 정보를 연결한다. Preview에서 실제 마이그레이션과 호환되는지 확인하고 운영 반영 후 두 브라우저로 재검증한다. |
| **Cloud Run** | `asia-northeast3`의 기존 서비스에 FastAPI 실제 버전을 소스 배포한다. 포트는 Cloud Run이 주는 `PORT`로 듣는다. RAG 쿼리 자격과 모델 키·서버 간 인증값을 서비스 런타임에 연결한다. 비밀값은 Secret Manager로 제공하고 런타임 서비스 계정에 필요한 비밀의 읽기 권한을 준다. |
| **Supabase** | 한 프로젝트 안에 민원과 RAG 스키마·권한을 구분한다. 민원 쓰기는 Next.js, 검색은 FastAPI가 담당한다. 익명 접근을 차단하고 역할별 범위를 점검한다. 이전 스키마와 호환되는 마이그레이션을 먼저 확인한 뒤 애플리케이션을 배포한다. |

환경변수 이름은 기존 팀 브랜치에 이미 정의된 이름을 우선 사용한다. 최소 설정 목록에는 Cloud Run 기본 URL, 서버 간 인증값, Next.js의 민원 DB 연결, FastAPI의 RAG 읽기 연결, 모델 ID·키, 자료 버전을 기록한다. 키·DB 자격증명은 서버 환경에 저장하고 배포 기록에는 값 없이 설정 여부만 적는다.

배포 확인 순서는 `Cloud Run /health → Vercel /api/ai/health → DB 저장·조회 → AI 근거 응답 → 모델 장애 시 직접 이관`이다. 배포 기록에 Vercel 커밋·URL, Cloud Run 리비전, 마이그레이션 버전, 자료 버전과 실패 재현 절차를 남긴다. 오류는 요청 ID·시간·오류 코드로 추적하고 토큰·시민 발화 원문은 배포 로그에 남기지 않는다. 새 버전에서 문제가 생기면 서비스별 직전 정상 배포로 복귀할 수 있는지 확인한다.

## 7. 제출 수용 시험

| 시험 | 통과 기준과 남길 증거 |
| --- | --- |
| **배포 연결** | 제출 웹 주소에서 헬스 체크 200. AI 인증 없이 추론 요청은 거절된다. 실제 버전으로 시험한 배포 커밋과 리비전을 함께 기록한다. |
| **AI 장애와 바로 연결** | 근거 없음, 모델 타임아웃 또는 FastAPI 접속 실패를 각각 유도한다. 시민이 버튼을 누르면 인증된 다른 브라우저의 콘솔에서 원문·사유·미확인 상태를 본다. 중복 클릭·재요청에도 하나의 이관 ID만 존재한다. 시작 직후 빈 문맥 연결과 AI 응답 중 연결도 각각 확인한다. |
| **승인·재시도·권한** | 수정 뒤 최신 요약만 승인된다. 미확인·생략·무응답은 자동 승인되지 않는다. DB 실패 후 재시도는 같은 건을 사용한다. 익명/시민 토큰의 콘솔 접근과 타 세션 접근이 거절되고, 동시 담당 지정은 한 번만 성공한다. |
| **기존 세 시연** | [대본](../../demo/demo-script.md)과 [턴별 정답](../../demo/golden-turns.json) 기준으로 대형폐기물 안내, 교통카드 정책/개인 입금 이관, 수도 요금 근거 부족과 상담사 요청을 검증한다. 재설명 횟수, 누락·금지 표현·출처·상태를 기록한다. |
| **대본 밖 문의·RAG** | SC-013의 독립 15문항, SC-015의 미확보 분야·자치구, SC-016의 복합 문의, SC-018의 필수 질문 한도·연결 요청·제안 거절을 시험한다. 타 구·만료·대체·미검증·개인 조회는 확정 답변 금지. 확장 복지 질문은 검증 자료만 사용한다. |
| **음성·화면** | 실제 제출 HTTPS와 시연 Chrome으로 한국어 음성 입출력을 확인한다. 마이크 거부 시 텍스트로 동일 흐름을 완료한다. 팀 외 검토자가 안내 없이 핵심 버튼을 찾고, 연결 버튼·1번 키·연결 상태·부분 수정·담당 창구 선택이 읽히고 동작하는지 확인한다. |
| **복구와 지표** | SC-023은 제출 주소에서 새로고침과 앱 재배포 뒤 세션·대기열이 유지되는지 확인한다. 종료 확인·대기·담당 지정·처리 완료 이벤트로 모의 지표를 재계산한다. 비식별 개선 후보 1건은 승인 전 검색 근거로 쓰이지 않으며 별도 시험 자료 버전으로 검증한다. |
| **제출물** | 실제 통과표, 시민 화면·콘솔 주소, 자료/모델/배포 기록, 세 시나리오 녹화, 정책 변경 시나리오 오프라인 백업, 3분 시연 리허설 기록을 확보한다. 미실행 시험을 통과로 표시하지 않는다. |

기존 [성공 기준](spec.md#success-criteria-mandatory)의 필수 항목을 위 시험에 대조한다. 기존 명세가 후순위로 둔 성능 대량 측정(SC-011)과 폭넓은 신규 분야 확장 시험(SC-014)은 별도 목표로 기록한다. 제출 전 가장 먼저 확인할 기능은 **AI 없이 접수되고, 상담사가 다른 브라우저에서 같은 민원 건을 읽을 수 있는지**다.
